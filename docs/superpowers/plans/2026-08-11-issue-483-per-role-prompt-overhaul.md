## Task 1: Versioned per-role system-prompt templates + loader (TDD)

**Outcome:** A new, small, fixture-tested loader that reads one Markdown file per role from a new versioned directory and returns its content + a version string, or `undefined` for roles with no template (e.g. `fixer`).

**Design guidance (not prescriptive — implementer's judgment governs the actual code):**
- New directory `harness/system-prompts/` with one `.md` file per targeted role: `planner.md`, `developer.md`, `plan-reviewer.md`, `code-reviewer.md`, `tester.md`. Each file is short (system-prompt-sized, not task-brief-sized): the role's non-negotiable identity/behavior rules — the kind of thing that should hold even if the per-task user message content gets truncated or ignored. Do not copy the existing `harness/roles/*.md` content verbatim; that content is already delivered elsewhere. Write new, tighter content appropriate for a system-prompt surface.
- A tiny manifest for versioning only — e.g. `harness/system-prompts/manifest.json: { "version": "2026.08.11-v1" }`. No fragment-matching machinery is needed here (unlike `versioned-harness.ts`'s `FragmentSchema`): the role name maps directly to `<role>.md`, one file, no priority/stack/tag matching. Building fragment-matching for a single-axis, one-file-per-role lookup would be speculative generality — skip it.
- A small class/module (e.g. `packages/harness/src/system-prompt-loader.ts`, mirroring `VersionedHarnessRepository`'s constructor-takes-a-dir shape) with a `select(role: AgentRole): Promise<{ version: string; content: string } | undefined>` (or equivalent) — returns `undefined` when `<role>.md` doesn't exist (covers `fixer` and any future unmapped role) rather than throwing.

**Acceptance criteria:**
- Loader is unit-tested against real, checked-in fixture files on disk (same pattern as `packages/harness/src/versioned-harness.test.ts` — direct assertions on real fixture content, no mocking, no snapshot library) — covering: a role with a template returns content + version; a role without one (`fixer`) returns `undefined`; version string matches the manifest.
- The five role `.md` files exist with real, role-appropriate content (not placeholder text) and are cited against `cli-capabilities.md` in a one-line comment or doc reference explaining which validated surface they're meant for.
- `fixer` has no template file — its absence is the mechanism for "out of scope," not an if-statement anywhere.

**Out of scope:** wiring this into the executors or orchestrator (Task 2). Touching `harness/roles/*.md` or `harness/manifest.json` (existing layer, untouched).

## Task 2: Wire system-prompt content into the contract and both CLI executors (TDD)

**Outcome:** `AgentExecutionRequest` carries the new role's system-prompt content end-to-end from the orchestrator's role-based selection (mirroring the existing `harness.select(...)` call site) through to each executor's CLI invocation, using each CLI's real system-prompt-equivalent flag.

**Context:**
- `AgentExecutionRequestSchema` (`packages/contracts/src/agent.ts:68-84`) needs one new optional field, e.g. `systemPrompt: z.string().optional()` (content only — version is a run-metadata/evidence concern, not something the executor needs). `ExecutionAgentRequestSchema` (`packages/contracts/src/execution-plane.ts:25`) derives via `.omit({cwd: true})`, so it inherits the new field automatically.
- Orchestrator wiring: `packages/orchestrator/src/workflow-orchestrator.ts:2753` (`const harness = await this.harness.select({...})`) is the existing role-based selection call site to mirror — add a sibling call to Task 1's loader, keyed on `step.role`. The `agent: {...}` object literal passed to `this.executionPlane.submit(...)` (around `workflow-orchestrator.ts:3455-3470`) is where the resolved content becomes part of the request. Also mirror the existing `harnessVersion: await this.harness.version()` pattern (`workflow-orchestrator.ts:1344`, `:3624`) for the new loader's version, so it lands in the same run-metadata/evidence trail the harness version already uses — for audit, not for the executor's own request payload.
- `packages/executors/src/claude-executor.ts:24-47` (`invocation()`): when `request.systemPrompt` is present, add `'--append-system-prompt', request.systemPrompt` to `args` (argv array — `execa`, no shell escaping needed). When absent, behavior is byte-for-byte unchanged from today.
- `packages/executors/src/codex-executor.ts:20-49` (`invocation()`): when `request.systemPrompt` is present, add `'-c', <toml-config-arg>` to `args`. Codex parses `-c key=value` as TOML — use a **TOML literal string** (single-quoted, `'''...'''` for multi-line): `` -c `developer_instructions='''${request.systemPrompt}'''` ``. TOML literal strings take content verbatim with zero escaping (no backslash processing), which is exactly right for markdown role content — the only constraint is the content must not itself contain the three-character sequence `'''`. Guard this explicitly (throw a clear error, or assert in a test fixture) rather than silently producing a broken CLI invocation if it ever does. Do not use `instructions` (dead/unwired per the research doc) or `model_instructions_file` (discouraged, full-replace).
- When absent, Codex's args are byte-for-byte unchanged from today.

**Acceptance criteria:**
- New contract field is optional and backward compatible — existing callers/tests that don't set it are unaffected.
- Unit tests on `claude-executor.ts` and `codex-executor.ts` cover: `systemPrompt` present → correct flag/value appended to `args`; `systemPrompt` absent → args identical to current behavior (regression guard against accidentally always adding a flag).
- A focused test on the Codex TOML value construction covers content containing a literal quote (`"`), a backslash, and a newline — proving the literal-string choice actually avoids escaping bugs for realistic role-prompt content — plus the guard behavior when content contains `'''`.
- Orchestrator wiring test (or extend an existing orchestrator test) confirms a step with role `developer` (has a template) produces a request with `systemPrompt` set, and a step with role `fixer` (no template) produces a request with `systemPrompt` unset — proving the end-to-end selection, not just the loader in isolation.

**Out of scope:** the real-mode A/B run and evidence doc (Task 3). Any change to `prompt-compiler.ts`'s `REQUEST.md` content (existing layer, untouched — this task only adds the new system-prompt layer alongside it).
